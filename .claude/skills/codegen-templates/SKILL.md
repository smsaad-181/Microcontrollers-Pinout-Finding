# Code generation

1. Input is a `Recommendation`; output is files + install notes. **No pin literal may originate
   anywhere except `assignments[]`.** A test parses generated code and checks every pin number.
2. Library choice per (module, framework) comes from a catalog evidence record of `kind: library`
   (maintainer repo, tag, init API location). Use the `context7` MCP to read current docs, then
   confirm the version/tag on the maintainer repository. No library fact ⇒ generate pin defines only
   and say "library not verified".
3. Header block in every file: generated by Pinout Finder, catalog version + hash, board + variant,
   warnings that need hardware action (pull-ups, dividers, separate supply).
4. ESP32 Arduino: use `Wire.begin(SDA, SCL)`, `SPI.begin(SCK, MISO, MOSI, CS)` with explicit pins;
   per-device SPI clock ≤ the engine's clamp. AVR: fixed hardware pins — still emit constants.
   MicroPython: `machine.I2C(id, sda=Pin(..), scl=Pin(..), freq=..)`, `machine.SPI(...)`.
5. Debounce for inputs flagged by errata (e.g. ESP32 GPIO-3.11 on 36/39) is included as code + comment.
6. CI: `arduino-cli core install` with pinned core versions; `arduino-cli lib install "<name>@<ver>"`;
   compile per FQBN; `mpy-cross` for MicroPython syntax. All pinned in the workflow.
7. Ambiguous variants → labelled alternatives; never an invented API.
